# Standard events and the local API

Everything on screen is driven by one record type: the **standard event**, a report of one session's state. For hook-driven agents it is the *output* of the reducer (adapters map hooks to signals, the reducer produces the state); scripts and cron jobs post it directly as *input*, and the reducer adopts what they report. The UI never knows which agent produced it. The authoritative definition is `schemas/event.schema.json`; this page explains the fields.

## Example

```json
{
  "schema_version": 1,
  "agent": "claude-code",
  "session": "abc123",
  "parent": null,
  "project": "ai-pii",
  "space": "office",
  "state": "waiting_user",
  "waiting_on": { "reason": "approval", "target": "Bash: npm" },
  "result": null,
  "detail": "Bash: npm",
  "tokens": { "in": 1200, "out": 340, "scope": "turn" },
  "ts": "2026-10-19T12:30:00Z"
}
```

## Fields

| Field | Meaning | Required |
| --- | --- | --- |
| `schema_version` | Always `1` for this format | yes |
| `agent` | Agent kind = character species (`claude-code`, `codex`, or any slug for scripts) | yes |
| `session` | Session = one character. Children without their own id use `<parent>/<child id>` | yes |
| `state` | `idle`, `working`, `waiting_dependency`, `waiting_user`, `error`, `done`, `unknown`, plus `paused`/`cancelled` when the adapter supports them | yes |
| `ts` | Event time, ISO 8601 | yes |
| `waiting_on` | `{ reason, target }`; `reason` ∈ `approval`, `input`, `child`, `tool`, `schedule` | when state is `waiting_user` or `waiting_dependency` |
| `parent` | Parent session for subagents. In a direct report it attaches the session under that parent (the parent appears if it is new); under a parent that has ended, the session is ended too | no |
| `child_type` | For a subagent: its kind as its agent names it (Claude Code's `agent_type`, a Codex thread's role such as `worker` or `reviewer`), set by the daemon from the hooks; absent for a top-level session; ignored on input |
| `background` | Daemon-set, informational: how much of the session's background work (commands, subagents, monitors it left running) still ran when its agent last said, as its hook counted it (Claude Code's `Stop` list); absent when none. The session rests, is not finished and does not go home while it runs |
| `delegations` | `{ open: [{ target, initiation, since }], returned }`: work the session handed to other sessions through a tool its adapter classes as `delegation` (today the Claude app's cloud session start): what is still out — where (`cloud`, …), who asked (`user_asked`, `own_initiative`), since when — and how many results came back as task-notification prompts. A layer over `state`, never a wait; absent when there is neither; set by the daemon; ignored on input |
| `project` | Project folder name = desk group (daemon derives `basename(cwd)` when absent) | no |
| `cwd` | Working directory, used for project and space rules only | no |
| `space` | Room override; otherwise classified by [spaces.md](spaces.md) | no |
| `lifecycle` | `active` (default) or `ended`. A direct report with `ended` ends the session: the character leaves, and so do its children. A later report brings it back, unless the session's parent has ended; `active` changes nothing by itself | no |
| `result` | `{ outcome, at, summary }` of the last turn; survives `done → idle` | no |
| `detail` | Current tool or waiting target, ≤ 64 chars, never conversation content | no |
| `origin` | `human`, `scheduled`, `automation`, `sdk`, `external`, `unknown`. The first report that names one sets it; children without one inherit their parent's. A session that is a scheduled task's own thread or one its run opened (Codex: `automations.target_thread_id` or `automation_runs.thread_id` equal to the session id) is sent as `scheduled` with the task's name as `title`, whatever its reports said | no |
| `tokens` | Token counts with `scope` = `event` (delta), `turn`, or `session_total`; see [usage-and-cost.md](usage-and-cost.md) | no |
| `model` | Model id if known | no |
| `ttl_s` | Direct reports only: seconds until the state is considered stale | no |

Subagent creation is not a state: it is the first event of a new `session` whose `parent` is set. Movement is decided by the UI and never appears in events.

## Compatibility

Fields are only added; unknown fields are ignored; `schema_version` changes only for incompatible changes. Full rules in `schemas/README.md`.

## Daemon HTTP API (loopback only)

All routes are under `http://127.0.0.1:<port>/v1`. Every route except `GET /health` requires `Authorization: Bearer <token>` (`~/.agent-office/token`), reads included, because session lists show working folders; the browser UI reads with a UI token obtained through a one-time launch code (`agent-office ui`) ([privacy-security.md](privacy-security.md)).

| Route | Purpose |
| --- | --- |
| `GET /health` | `{ version, pid, started_at, schema_versions, config }`; no auth. Detects a stale daemon after an upgrade; `config` is `ok`, or `defaults` when `config.json` could not be used. With `?challenge=<hex>` it also returns `proof`, which lets the hook check that it is talking to this daemon before it sends anything |
| `POST /ui/launch` | Owner's token only: `201 { code, expires_in_s }`, a one-time launch code for the browser UI, valid for 60 s |
| `POST /ui/session` | No token: `{ "code" }` → `201 { token }`, a UI token that may call the read routes (`/sessions`, `/attention`, `/stream`, `/usage`, `/limits`) and lapses after 12 idle hours or a daemon restart; `401 launch_code_invalid` for an unknown, used or expired code |
| `POST /hook/{agent}` | Hook envelopes (`schemas/hook-envelope.schema.json`) |
| `POST /events` | One standard event or an array of ≤ 100; `202` with `{ "results": [{ "index", "ok", "error"? }] }` |
| `GET /sessions` | Current snapshots (what the session list beside the scene shows): `{ "sessions": [<standard event>, …] }`, where `ts` is the session's last signal time |
| `POST /sessions/:id/dismiss` | Owner or UI token, no body: the owner sends a session home (rule G2). A top-level session that is resting, finished, cancelled, failed, paused, quiet or waiting for an answer (Claude Code leaves a wait behind when a request is denied with Esc) ends with its children; its agent is not touched, and its own next signal brings it back. `200 { ok }`; `404` for an unknown session, `409` (`not_dismissible`) for a child, an ended session, or one at work (`working`, `waiting_dependency`). The viewer answers `405` |
| `POST /sessions/:id/open` | Owner or UI token, no body; `:id` is URL-encoded (a child opens its top-level session). Takes the user to the session: brings its tmux pane, iTerm2 session, Terminal tab or app forward while it runs, or opens it again with the adapter's `open_cli` in a new window of the terminal it ran in when its process is gone (never a running one). Means come from the descriptor's `open`; nothing is typed into a session. `200 { means, reason, command }`: `means` is `tmux`, `iterm`, `terminal_tab`, `app`, `resume` or null; `reason` (when null) `ssh`, `unsupported` (no desktop actions on this OS yet: Linux, Windows) or `not_found`; `command` is the resume command to run by hand, for a session not running here. `404` for an unknown session, `409` while an open of it runs. macOS asks once per terminal app before the first AppleScript |
| `GET /stream` | Server-sent events: `sessions` (the full list; a session's `launcher`, when known, says where it runs: `claude-app`, `codex-app`, `vscode` or `terminal`, from the path of its verified process; its `title`, when the daemon read one, is the title the agent's own app shows: Claude Code's session title from its transcript, a Codex thread's name from Codex's state database; a subagent's `title` is the nickname its agent gave it (a Codex worker's or reviewer's) and its `child_type` its kind; never in screen-share mode, and to a viewer only at `full`) and `attention` (the attention list, below) on connect, then `session` (one standard event) for each change and `attention` (the whole list again) whenever the list changes; `schedule` (the scheduled tasks, as `GET /schedule`, on connect and again whenever it changes), `settings` (`{ wander_after_s, cast, species, board, schedule, labels, needs_you_marker, needs_you_glow, language, notification_sound }`, the owner's `scene.wander_after_s`, `scene.cast`, `species`, `scene.board`, `schedule.bench_before_min` and `schedule.rest_after_min` with the clock zone `time_zone`, `labels.show` as `{ show }`, `scene.needs_you_marker` (`{ stronger_after_min, strongest_after_min }`, null for never), `scene.needs_you_glow` (boolean), `ui.language` (`auto`, `ko` or `en`) and `notifications.sound` as `notification_sound` (`chime`, `animal` or `off`; what the desktop app and the viewer play), after the opening lists) and `notification` when the daemon decides to notify ([notifications.md](notifications.md)): `{ id, kind, signal, session, since, agent, title, target, turn_s, opens }`, where `kind` is `needs_you` or `ready`, `signal` the needs-you signal or `ready`, `title` the project of the session or of its top-level parent (null when unknown or in screen-share mode), `target` the wait's tool target (null when none, for `ready`, or in screen-share mode), `turn_s` the finished turn's length (`ready` only) and `opens` what a click shows (`session` or `queue`, from `notifications.channels.desktop.click_opens`); none are sent on this stream while `notifications.channels.desktop.enabled` is false (the viewer's and web push still are); `controls` (as `GET /controls`, after `warnings`, and again whenever it changes; not on the viewer's stream); `warnings` (`{ hooks }`, after `settings`, and again whenever it changes): `hooks` is null, or `{ code, since }` while hooks are not reaching the daemon — `hooks-not-delivered` (the launcher found nothing to run a hook with, at `since`, after the last signal any hook delivered) or `launcher-target-missing` (the Node or program the launcher names is gone; `since` is the last such finding, or null); the viewer's stream does not send it. A comment line every 15 s keeps the connection open. Usage updates will join later |
| `GET /board?year=YYYY` | The office board's record of a local calendar year (default the current one): `{ today, year, days: [{ day, completed, cancelled, solo, failed, waits, long_waits }], months: [{ month, target }], issues_today: [{ session, kind, at }] }`. `days` lists only observed days; `solo` (turns done without waiting for the owner), `failed` (failed or lost mid-turn), `waits` (the owner's answered waits) and `long_waits` (over five minutes) are null for a day rolled up before they were counted; `kind` is `error` or `lost`. Main listener only |
| `GET /usage?days=N`, `GET /limits` | Tokens per local day, agent, project and model for the last N days (1–400, default 7), and the newest observation of each rate limit (shapes in [usage-and-cost.md](usage-and-cost.md) §10) |
| `GET /schedule` | The scheduled tasks the agents' own schedulers plan (Codex, Claude desktop, OpenClaw, Hermes and OpenCode; pi reports an unavailable native source): `{ sources: [{ agent, outcome, code, at }], tasks: [{ key, agent, name, project, cwd, status, kind, rrule, next_run_at, last_run_at, thread: { session, linked } | null, run: { session, status, at, linked } | null, missed: { at } | null, unsure: { at, reason } | null, observed_at }] }`. `outcome` is `ok`, `empty`, `absent`, `unreadable` or `unsupported` (with `code`); `thread` is the task's own thread when its scheduler names one (a Codex heartbeat task runs as turns of it); `thread.linked` and `run.linked` say the daemon knows that thread as a session (then that session's `origin` is `scheduled` and its `title` the task's name); `missed` an occurrence that passed with no run while the daemon watched (also a `needs_you` entry, signal `schedule_missed`, under the task's `key`); `unsure` one it could not watch all the while (`daemon_down`, `source_down`, `execution_unconfirmed`). Optional additive fields: `native_status` (`done`, `completed`, `error`) preserves a known definition state; `rule` carries native cron/interval/at metadata separately from RRULE; `running_at`, `last_attempt_at`, `last_status` carry scheduler evidence; `can_confirm_run` and `can_detect_missed` say whether the source can establish execution or rule out an in-flight occurrence. A run with `evidence: session_created` is an exact identity link, not execution proof. Ambiguous multiple tasks targeting the same session do not assign an arbitrary task name. `code: no_native_scheduler` means no native source is available, not an empty list of tasks. Not served by the viewer |
| `GET /attention` | The attention list ([notifications.md](notifications.md)), derived by the daemon from the snapshots and the recorded state changes, because the session event alone cannot tell the signals apart: `{ "needs_you": [{ session, signal, since }, …], "ready": [{ session, since, turn_s }, …], "long": [{ session, since, basis, start_known, waited_s }, …], "opened": [{ session, since }, …], "away": [{ session, since }, …], "internal": [{ session }, …], "ended": [{ session, since, by }, …] }`. `needs_you` lists user waits first (`signal` `approval` or `input`, children included, longest first), then failed turns (`error`, children included), then top-level sessions whose process ended mid-turn (`lost`); `since` is when the wait, failure or loss began. A session gone quiet (`unknown`) is not listed (since 2026-10-28). `ready` lists top-level sessions whose turn finished with no prompt since, oldest first; `since` is the end of the turn and `turn_s` its length, null when its start was not seen. `long` lists top-level turns that have run longer than `states.long_turn_min` (a quiet marker, never notified), not counting the session's own waits for the user (`waited_s`); `since` is the turn start, or the first observation when `start_known` is false; `basis` is `threshold` (`relative` is reserved). `opened` lists top-level resting sessions started, resumed or cleared with no turn since (an app reopening old sessions, a session never asked anything), oldest first; `since` is that start; the office stands them faded by its front until their first prompt (since 2026-10-30; before, it left them out). `away` lists top-level sessions that have rested (idle after a finished, cancelled or failed-over turn, `done`, `cancelled`, `paused`), been quiet (`unknown`) or been only opened for `states.away_after_min` minutes (default 30; 0 turns it off), oldest first; `since` is when the rest began (the end of the turn, when it went quiet, or when it was opened); the office leaves them out until their next turn and the home tab lists them (an opened one stays under `opened` as well). A session at work, waiting for the owner or failed is never away. `internal` lists top-level active Codex threads that Codex's own thread list does not have once they are 5 s old (threads the Codex app runs for itself: they send the same hooks but have no rollout and cannot be opened), by id; such a thread and its children are in no other list, whatever they wait on, and the office leaves them out for good; the All tab shows them as "앱 내부 작업" only on request (since 2026-10-29; hidden by default since 2026-10-30). `ended` lists every top-level session that ended and the daemon still remembers (a day after its last signal), oldest first, with `since` (the end) and `by`: `owner` (sent home with "목록에서 숨기기", rule G2), `lost` (its process went mid-turn; also under `needs_you`) or `agent` (its own end, its process going at rest, or its process stopped at the owner's request, rule G3, which is never listed as lost); the home tab ("퇴근") shows them with away sessions, latest first, with how the last turn ended (since 2026-10-29). A turn starts with a prompt, or when a resting session starts working without one; recovering from silence or a pause continues the turn it interrupted. The stream carries the same list as `attention` events |
| `GET /notes` · `PUT /sessions/:id/note` | The owner's notes, `{ notes: { <session>: { nickname, description, watched, alert_on_rest } } }`; written from the computer only (owner or UI token): the body has all four fields (`nickname` up to 24 characters, `description` one line up to 120, both null or empty to clear; `watched` and `alert_on_rest` booleans), control characters are dropped, line breaks become spaces, and clearing every field deletes the note. `404` for a session the daemon does not know, `400 invalid_note` for a body of another shape. A change is sent on the stream as `notes` (the whole map, also sent on connect). The viewer gets `GET /notes` and the `notes` events with the nickname and star only (the description at `remote_view.detail: full`, never `alert_on_rest`) and answers `405` to the write |
| `POST /sessions/{id}/open` | Open the session (window focus or CLI resume) |
| `POST /sessions/:id/controls/{stop,restart}` | Owner or UI token, header `Idempotency-Key` (8–64 of `A-Za-z0-9_-`, one per click), body `{ "instance": <the 16-hex process token from GET /controls> }`: stop the session's agent process, or stop it and open the same conversation in a new terminal window ([click-panel-and-controls.md](click-panel-and-controls.md)). The viewer answers `405` |
| `POST /services/:agent/controls/{start,stop,restart}` | Owner or UI token, header `Idempotency-Key`, body `{ "instance": <the 16-hex token from GET /controls> }` (not needed for `start`): run a background service's own command ([click-panel-and-controls.md](click-panel-and-controls.md)). `202 { request }`, `200 { request }` for the same key again, `400` `idempotency_key` or `instance`, `404` for an unknown control, `409` with the reason (`not_declared`, `unsupported_platform`, `busy`, `status_unreadable`, `status_shape_unknown`, `identity_unverified`, `run_in_progress`, `run_due_soon`, `instance_changed`, `idempotency_key_reused`). The viewer answers `405` |
| `POST /controls/start` | Owner or UI token, header `Idempotency-Key`, body `{ "agent", "cwd" }`: open a new session of the agent in that folder in a new terminal window, with an id the daemon chooses and no prompt. `202 { request }`; `400 folder_missing` (not an existing absolute folder); `409` `not_declared`, `unsupported_platform`, `hooks_missing` (no hook of that agent ever reached the daemon, so nothing could confirm the start) or `busy` |
| `GET /controls` | The lifecycle controls: `{ requests: [{ id, control, agent, session, status, step, requested_at, resolved_at, reason, evidence }] (the 20 newest), available: { <session>: { controls: ["stop", "restart"], instance } }, start: { agents, folders } }`. `status` is `requested`, `sent`, `confirmed`, `failed` or `timeout`; `step` follows a restart (`stopping`, `stopped`, `starting`, `recovered`) or a start (`launching`, `bound`); `session` is null for a start until it is bound; `reason` names why nothing (more) was done (`identity_unverified`, `app_owned`, `no_tty`, `inventory_mismatch`, `inventory_unavailable`, `instance_changed`, `signal_not_permitted`, `still_running`, `terminal_not_opened`, `no_process`, `no_first_signal`, `daemon_restarted`, `internal`, `command_failed`, `command_timeout`, `not_confirmed`, `service_not_installed`, `status_shape_unknown`, `status_unreadable`, `run_in_progress`, `run_due_soon`); `evidence` holds times and counts only (`signalled_at`, `instance_gone_at`, `session_end_signal`, `descendants`, `leftover_descendants`, `bound_at`, `new_instance_started_at`, `after_daemon_restart`, `exit_code`, `command_done_at`, `confirmed_at`). A request of a background service has `service` set and `session` null, and `step` `running_command` then `confirming`. `available` lists the sessions that can be stopped or restarted now with the token of the process the daemon saw; `start.folders` the folders of known sessions (at most 12, newest first); `services` the declared background services found on this machine, `[{ agent, state: "running" | "stopped" | "unknown", controls, instance, note }]`. Not on the viewer |
| `GET/PUT /notes/{session}` | Nickname and description |
| `GET /open/{session}` | Browser-friendly redirect used by notification clicks: performs the open and shows a one-line page |

Outside `/v1`, `GET /` and the files next to it serve the built browser UI (no token, a strict Content-Security-Policy); `404 ui_not_built` until `npm run build:ui` has run.

Rules: inputs are validated against the schemas, strings are control-character-stripped and truncated, `Host` must be loopback, no CORS headers, responses never echo raw input.

### Viewer listener (server mode, off by default)

When the daemon runs on a server and is watched from a phone or tablet, it can open a second, **read-only** listener. It stays off unless its bind address is given on the command line: `config.json` cannot enable it; loopback and private addresses (RFC 1918, `100.64.0.0/10`, `fc00::/7`) are accepted with a warning that a plain LAN address is unencrypted, and wildcard and public addresses are refused. A bind failure is logged and retried and never stops the app. It serves only the UI's static files, `GET /health`, `GET /sessions`, `GET /attention`, `GET /usage`, `GET /limits`, `GET /stream`, `POST /pair` and `/push` (the device's own web push: `GET` answers `{ key, subscribed }`, the daemon's VAPID public key in base64url and whether this device has a subscription; `PUT` with the browser's subscription JSON `{ endpoint, keys: { p256dh, auth } }` sets it, refused with `400` `subscription_endpoint` unless the endpoint is an https address of Apple's, Google's, Mozilla's or Microsoft's push service, or `subscription_keys`; `DELETE` removes it; each answers `{ subscribed }`); a write route of the main API gets `405` and anything else `404`, so nothing reachable from the network can inject an event, open a session or change a setting. Every route, `health` included, needs a viewer token: each device gets its own, separate from the hook and UI tokens, redeemed once from a short-lived pairing code with `POST /pair` (a few attempts, then a new code) and sent only in the `Authorization` header, never in a URL (the viewer UI reads the stream with `fetch`); the settings tab lists and revokes them. What the viewer may show follows `remote_view.detail`: `status` (default) sends the name tag (nickname or project folder name), state and waiting reason; `targets` adds the current tool or waiting target; `full` adds the user description. The working folder is never sent, and below `full` the usage route is per agent, not per project. Reach the listener over an SSH tunnel or a private network you install (WireGuard-class, for example Tailscale); it is not meant for the public internet and does not terminate TLS. A proxy on the same machine may serve it over HTTPS (`tailscale serve --bg http://127.0.0.1:<viewer port>` gives `https://<machine>.<tailnet>.ts.net`): `--viewer-host <that name>` makes the viewer accept it as `Host` (with or without `:443`) and the origin `https://<name>`, and pairing then shows `https://<name>/`; web push needs such an address. The stream's `notification` events (above) go to the viewer at its detail level also while `notifications.channels.desktop.enabled` is false, and with web push to each subscribed device. Implemented 2026-10-27 (moved ahead of packaging): `agent-office daemon --viewer <address>[:<port>]` (default port 47650; `npm run app -- --viewer <address>` passes it to a daemon the app starts; a failed bind is logged and retried every 30 s). The owner gets a pairing code from `POST /v1/viewer/pair-code` on the main API (owner token only; `agent-office pair` and the tray's "기기 연결…" use it): eight characters without look-alikes, valid five minutes, once; at most three wait; five wrong codes from one network address lock that address out for 30 s (`429`), so nobody on the network can spoil the owner's code by failing on purpose. `GET /v1/viewer/devices` lists paired devices and `POST /v1/viewer/devices/<id>/revoke` removes one and ends its streams at once; both are owner-only on the main API. Devices survive restarts (only the token's SHA-256 is stored) and are forgotten after 30 days without use. The viewer accepts at most 64 connections and four streams per device. The viewer serves `GET /mode.json` (`{ "mode": "viewer" }`, so the page knows to ask for a code) and `GET /v1/sessions/<id>/resume` (`{ command }`: the resume command without the folder, for the card's "continue on the computer"); `GET /v1/health` there answers `{ version, machine, detail }`. At `status` the wait's target and the tool detail are empty, at `targets` the wait's target is sent, at `full` the detail too; `cwd` is always null. The viewer's `usage` and `limits` routes are not served yet (they wait for the lobby board).

## `emit` CLI

```bash
agent-office emit --agent cron-script --session nightly-backup --state working --detail "nightly backup" --ttl 120
agent-office emit --agent cron-script --session nightly-backup --state done --outcome completed
agent-office emit --agent cron-script --session nightly-backup --state error --outcome failed --detail "exit 3"
```

`emit` reads the token itself, asks the daemon to prove it holds the token before sending (as the hook does), and spools like a hook when the daemon is down, unreachable or busy; the daemon takes spooled events on its next drain. A session that only ever reports via `emit` goes `unknown` after its `ttl_s` and is ended after `unknown_gone_s`.

Options: `--agent` (slug), `--session`, `--state` (required); `--detail`, `--ttl <seconds>`, `--outcome completed|failed|interrupted|cancelled`, `--reason approval|input|child|tool|schedule` with `--target` (required for `waiting_user` and `waiting_dependency`), `--parent`, `--origin`, `--cwd`, `--project`, and `--ended` (lifecycle `ended`). Like the hook, it reads the token once more and resends after a `401`. Exit code 0 when the event was delivered or spooled, 1 when the daemon refused it (or took it without a readable answer), 2 for bad arguments (with the reason on stderr); nothing is printed on success.
